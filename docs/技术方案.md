## 0. 这份方案怎么对齐训练站

训练站不是「一个知识问答页面」，它是**一条 9 阶段、27 项任务、9 道关卡、四个阶段作品的交付流水线**。站点把每项任务绑死在一个工具上（`brief / interview / workflow / whiteboard / phase / deliverables / prototype / assessment / engagement / client`），把每个阶段绑死在一句关卡验收语上，阶段作品强制提交 `summary / sections / evidenceIds / openQuestions` 四个字段，评分按 7 个维度、60 分通过。

所以本方案对应三层，**一层都不许缺**：

| 层 | 对应站点 | 本方案章节 | 缺了会怎样 |
|---|---|---|---|
| 流程层 | 9 阶段、27 任务、9 关卡 | 第 3 节追溯矩阵、第 7.1 节阶段引擎 | 系统退化成聊天框，交付物无法被关卡验收 |
| 业务层 | 门诊三个真实动作 | 第 7.5–7.8 节 | 只有流程空壳，门诊现场用不上 |
| 工程层 | 构建集成、测试评估的只读与审计要求 | 第 8–14 节 | 过不了阶段 5 的「可复现运行」和阶段 6 的「评估可审查」 |

一句话：**站点定义「要做哪 27 件事、每件事交什么、谁来点头」，本方案定义「这 27 件事在门诊场景里怎么被系统承载」。**

## 1. 一句话方案

**把「号源不一致」和「分诊信息不全」做成一个只读、可解释、必须人工确认的协同助手：结论由确定性规则算，模型只负责翻译成人话和补全信息，任何写操作都不由系统自动执行；同时把 FDE 九阶段的 27 项任务做成可提交、可评审、可追溯的工作台。**

## 3. 九阶段 27 任务 → 系统能力（追溯矩阵）

> 读法：`REQ-Sx-y` 是本仓需求编号，与站点任务一一对应；「谁确认」是**具名角色**，不是「相关部门」；「验收断言」是能在 harness 里跑出 true/false 的句子。
> 工具列用站点原文标签，不改名。

### 阶段 1 · 业务挖掘（`opportunity`）

| 编号 | 任务 | 工具 | 系统做什么 | 谁确认 | 验收断言 |
|---|---|---|---|---|---|
| REQ-S1-1 | 识别业务机会 | `brief` | 事件卡片：触发事件、影响面、维持现状的损失，三栏必填 | 门诊部主任 | 缺任一栏不许提交；损失必须是可换算的量 |
| REQ-S1-2 | 建立现状基线 | `workflow` | 指标卡：分子、分母、时间窗、样本来源、测量责任人，五项齐全才算「已采集」，否则置「待采集」 | 门诊部主任 | 五项缺一 → 状态强制为「待采集」，不许写成结论 |
| REQ-S1-3 | 确认立项与决策链 | `interview` | 利益相关者地图：发起人、使用者、出资者、审批者；四人不得重复 | 门诊部主任 | 四类人齐全且互不重合，否则 gate 1 不通过 |

### 阶段 2 · 现场调研（`discovery`）

| 编号 | 任务 | 工具 | 系统做什么 | 谁确认 | 验收断言 |
|---|---|---|---|---|---|
| REQ-S2-1 | 开展角色访谈 | `interview` | 六视角 × 6 问 = 36 问；每问落一条 `EV`，含原话、来源、时间、状态 | FDE 负责人 | 36 问未齐 → `foundCount < 36`，阶段不完成 |
| REQ-S2-2 | 还原现状流程 | `whiteboard` | 泳道图 DSL：触发、输入、交接、人工判断、输出、异常路径；瓶颈节点必须挂责任人 | 导医组长 | 无异常分支的流程图判为不完整 |
| REQ-S2-3 | 四来源收敛与材料核对 | `workflow` | 四列表：Buyer / Brief / Industry / Operator；每条结论指到 `EV`；冲突并列不取平均 | FDE 负责人 + 门诊部主任 | 冲突条目必须保留双方原话，且各带 `EV` |

### 阶段 3 · 需求定义（`definition`）

| 编号 | 任务 | 工具 | 系统做什么 | 谁确认 | 验收断言 |
|---|---|---|---|---|---|
| REQ-S3-1 | 确定优先问题 | `phase` | 排序：业务损失 × 发生频率 × 可解决性；暂缓项必须写理由 | 门诊部主任 | 每个暂缓项都有理由，无理由不许暂缓 |
| REQ-S3-2 | 编写需求与边界 | `deliverables` | 需求卡：证据、使用者、业务负责人、输入输出、排除范围、异常处置，六项齐全 | 门诊部主任 + 分诊护士 | 六项缺一 → `E-1003`；无 `evidenceIds` 不许提交 |
| REQ-S3-3 | 约定验收标准 | `workflow` | 可执行样例 + 阈值 + 样本 + 评审人 + 拒绝条件（一例即失败项单列） | 医务科 | 「一例也不能接受」的项必须单列，不许混在百分比里 |

### 阶段 4 · 方案设计（`solution`）

| 编号 | 任务 | 工具 | 系统做什么 | 谁确认 | 验收断言 |
|---|---|---|---|---|---|
| REQ-S4-1 | 选定最小试点 | `phase` | 三方案比较：人工优化 / 确定性规则 / 模型；写清范围外事项与终止条件 | 三方评审（门诊部、医务科、信息科） | 选模型必须给「为什么不用规则」的理由 |
| REQ-S4-2 | 设计数据和系统边界 | `whiteboard` | 架构图 + 权限矩阵 + 接口契约 + 模型职责 + 人工复核节点 | 信息科 + 医务科 | 权限矩阵缺任一角色 → gate 4 不通过 |
| REQ-S4-3 | 报价与投入产出测算 | `roi` | 一次性实施、月运行费、首年净收益、ROI、回本时间、假设与验证计划 | 分管副院长（出资者） | 收益必须标「已验证 / 待验证」，待验证不许计入净收益 |

### 阶段 5 · 构建集成（`build`）

| 编号 | 任务 | 工具 | 系统做什么 | 谁确认 | 验收断言 |
|---|---|---|---|---|---|
| REQ-S5-1 | 落实数据与工具契约 | `prototype` | 字段字典、版本、权限、测试输入；合成适配与真实接口的差距清单 | 信息科 | 未列差距清单 → 不许进 S5-2 |
| REQ-S5-2 | 实现业务闭环 | `prototype` | 规则、模型、工具、人工复核四段分离；每个输出带 `trace_id` 与 `confirm_by` | 分诊护士 | 任一输出无法追溯来源/规则/确认人 → 判失败 |
| REQ-S5-3 | 实现异常与审计 | `prototype` | 超时、缺数据、冲突、越权、重复请求、降级六类路径 + 审计字段 | 信息科 + 医务科 | 六类路径缺一 → gate 5 不通过 |

### 阶段 6 · 测试评估（`validation`）

| 编号 | 任务 | 工具 | 系统做什么 | 谁确认 | 验收断言 |
|---|---|---|---|---|---|
| REQ-S6-1 | 建立评估集合 | `prototype` | 正常/边界/对抗/权限/故障五类用例，每例关联 `REQ` 与失败成本 | 质量评审人 | 最昂贵的失败无覆盖 → 评估集不合格 |
| REQ-S6-2 | 执行测试与重复评估 | `prototype` | 代码快照、执行模式（模拟/真实）、跳过项、重复 5 次结果、审计轨迹 | 质量评审人 | 报告缺快照或跳过项 → 不可复现，判失败 |
| REQ-S6-3 | 修复并回归确认 | `assessment` | 缺陷闭环：定位、修复、复测、未解决项、业务角色结论 | 门诊部主任 | 未解决项必须有「改变方案/停止试点」的处置 |

### 阶段 7 · 客户试点（`pilot`）

| 编号 | 任务 | 工具 | 系统做什么 | 谁确认 | 验收断言 |
|---|---|---|---|---|---|
| REQ-S7-1 | 准备受控试点 | `deliverables` | 试点用户、样本、时长、对照组、人工兜底、退出信号 | 门诊部主任 | 无退出信号 → 不许开始试点 |
| REQ-S7-2 | 开展用户验收 | `engagement` | 真实任务走正常与异常路径；记录操作成本、采用障碍、不通过项 | 分诊护士 + 导医组长 | 只走正常路径 → UAT 不算完成 |
| REQ-S7-3 | 核对价值与继续决定 | `workflow` | 同口径前后对比，扣除运行与人工成本；结论三选一：继续/修改/停止 | 分管副院长 | 口径与 S1-2 不一致 → 收益不可归因 |

### 阶段 8 · 上线交接（`handoff`）

| 编号 | 任务 | 工具 | 系统做什么 | 谁确认 | 验收断言 |

| REQ-S8-2 | 演练发布与回滚 | `deliverables` | 版本、窗口、灰度范围、回滚触发器、步骤；演练一次故障恢复 | 信息科 | 未演练回滚 → 不许上线 |
| REQ-S8-3 | 完成运维和用户交接 | `engagement` | 运行手册、培训、权限、资产清单、升级路径、签收记录 | 门诊部 + 信息科 | 无具名维护人 → 交接不成立 |

### 阶段 9 · 运营迭代（`operation`）

| 编号 | 任务 | 工具 | 系统做什么 | 谁确认 | 验收断言 |

## 4. 业务目标与可验收指标

| 目标 | 指标 | 现状 | 目标值 | 口径（分子/分母/时间窗/样本/责任人） |
|---|---|---|---|---|
| 减少号源不一致的处置时间 | 单例处置时长（分钟） | 38（现场观察 42 单） | ≤ 10 | 患者到导医台 → 给出确定答复；10 月工作日早高峰；导医组长测 |
| 减少分诊补录对队列的干扰 | 补录占比 | 8–15 例/日 | 下降 50% | 补录数 / 当日签到数；连续 2 周；分诊护士长测 |
| 让兜底动作可追溯 | 留痕率 | 加号约 40% | ≥ 95% | 系统可查记录 / 实际发生；月度；门诊部抽查 |
| 不引入新的医疗风险 | 越界输出 | — | **0 例** | 出现诊断结论或自动定科即判失败；全量审计 |

> 前三个指标受 `Q-01`（同步窗口边界）、`Q-02`（不一致真实例数）未关闭影响，当前只能作「待验证目标」，**不得写进验收承诺**；第四个是硬门槛，出现一例即下线。这与站点「哪些数字还只是估计」的追问是一致的。

## 5. 总体架构

```text
┌────────────────────────────────────────────────────────────────┐
│  调用方（院内网）                                                │
│  导医工作站 · 分诊台终端 · FDE 工作台（九阶段/27 任务）            │
└───────────────────────────┬────────────────────────────────────┘
                            │ HTTPS + JSON（统一 {ok,data,error}）
┌───────────────────────────▼────────────────────────────────────┐
│  FastAPI 应用层（Python 3.11）                                   │
│  ├─ 中间件：request_id → 审计 → 出站脱敏 → 统一错误               │
│  ├─ 流程域：/stages /steps /artifacts /gates /evidence           │
│  ├─ 业务域：/slot /triage /note /kb                              │
│  └─ 依赖注入：当前用户、角色、权限集、阶段上下文                    │
└───────┬───────────────┬────────────────┬───────────────────────┘
        │               │                │
┌───────▼──────┐ ┌──────▼───────┐ ┌──────▼──────────┐
│ 阶段引擎      │ │ 业务能力层    │ │ 知识库（RAG）    │
│ 27 任务状态机 │ │ slot/triage  │ │ SQLite + 本地向量 │
│ 关卡 rubric   │ │ note/kb      │ │ 条款级引用        │
└───────┬──────┘ └──────┬───────┘ └──────┬──────────┘
        │               │                │
        └───────────────┼────────────────┘
                        │ 仅脱敏后的结构化文本
                 ┌──────▼────────────┐
                 │ Ollama 本地模型     │
                 │ qwen2.5:7b-instruct│
                 │ nomic-embed-text   │
                 └───────────────────┘
        ┌──────────────────────────────────────┐
        │ 审计库（SQLite）：trace / gate / 拒答   │
        └──────────────────────────────────────┘
```

**关键点一：模型不在判定链上。** 号源能不能用、该走哪条流程，由 `slot_rules.py` 算；模型只把结论转成导医能对患者说的话。模型出错最坏是「话说得不好听」，不是「给错结论」。

**关键点二：关卡不是提示词。** 关卡评审用 7 维 rubric 打分，60 分通过，未过则 `next_stage_locked = true`。模型可以给分，但**通过与否由具名确认人签**，两者分开记录。

## 6. 技术栈（锁定，不替换）

| 层 | 选型 | 版本 | 为什么是它 | 不许替换的原因 |
|---|---|---|---|---|
| 语言 | Python | 3.11+ | 类型标注、`tomllib`、性能足够 | 作业约束 |
| Web | FastAPI | ≥0.110 | 原生异步、Pydantic 校验、自动 OpenAPI | 作业约束 |
| 服务器 | uvicorn | ≥0.29 | 与 FastAPI 标配 | 不额外引入 gunicorn |
| 数据校验 | Pydantic | v2 | 请求/响应双端校验 | 与 FastAPI 同源 |
| 模型服务 | Ollama | ≥0.3 | 本地部署、OpenAI 兼容接口 | 作业要求本地部署 |
| 生成模型 | qwen2.5:7b-instruct | — | 中文医疗文本稳、7B 可跑 8 GB 显存 | 可配置，不硬编码 |
| 向量化 | nomic-embed-text | — | 与模型同一运行时 | 避免第二套推理进程 |
| 向量存储 | SQLite（纯 Python 余弦 / `sqlite-vec`） | 3.40+ | 单文件、零运维、随仓交付 | **不引入向量数据库** |
| 配置 | PyYAML + 环境变量覆盖 | ≥6.0 | 与 `config.yaml` 约定一致 | 作业约束 |
| 评测 | 自建 harness（`harness/`） | — | 用例即 YAML、报告可交付 | **不引入第三方评测平台** |
| 日志 | 标准库 `logging`（JSON） | — | 无额外依赖 | 不引入 ELK/Sentry |

> 选型原则：**能用一个文件解决的，不引入一个服务。** 知识库不是 Milvus/Chroma，评测不是 LangSmith，日志不是 ELK —— 都属「没要求的中间件」。

## 7. 模块设计

### 7.1 阶段引擎（`domain/stage.py`）

承载站点 9 阶段 27 任务的状态机：

- 状态只有四个：`locked`（上一关未过）→ `open` → `submitted` → `passed`；
- 每个任务的 `tool` 决定前端打开哪个工作台，后端不猜；
- 提交作品强制四字段 `summary / sections / evidenceIds / openQuestions`，`definition` 追加 `requirements`，`solution` 追加 `model`，`build` 追加 `demoSpec`；
- 任一步 `submitted` 但未 `passed`，下一阶段保持 `locked`。

**为什么把状态机放在服务层而不是路由层**：路由只做参数校验，状态迁移要能被 harness 直接调用（不起 HTTP 也能测 27 条迁移）。放在路由层，测试就得起服务，回归会慢十倍。

### 7.2 访谈官（`domain/interview.py`）

- 六视角固定，每个视角 6 问，共 36 问，**顺序不可跳**；
- 每问必须产出：原话、来源（录音/单据/日志/观察）、时间、状态（三态）；
- 追问规则：回答里出现数字但无口径 → 追问口径；出现「大概/一般/有时候」→ 追问最近一次具体事件；
- 36 问未满，`foundCount < total`，S2-1 不许提交。

### 7.3 证据台账（`domain/evidence.py`）

- 编号 `EV-序号`，一记录一号，不重复、不借用；
- 状态：`已核实`（有原始单据/日志/截图）、`待核实`（仅陈述）、`已驳回`（被后一份材料推翻）；
- 引用检查：任何作品提交时，`evidenceIds` 必须全部能在台账里查到，查不到即 `E-1004`；
- 数字必须带口径五要素，缺一项由系统拒收，不靠人自觉。

### 7.4 关卡评审（`domain/gate.py`）

7 维 rubric，分数与结论分开：

| 维度 | 判什么 | 不通过示例 |
|---|---|---|
| `evidence` | 每条结论有 `EV` 或标「待核实」 | 把访谈猜测写成「已确认」 |
| `upstream` | 承接上一阶段已确认的编号与版本 | 需求引用了不存在的 `EV-999` |
| `fde` | 用了工作流拆解、结果风险矩阵、四来源收敛 | 只写「调研发现效率低」 |
| `outcome` | 动作连到业务结果、口径、样本、责任人 | 只写「提升效率」 |
| `risk` | 异常、权限、人工交接、停止条件、不做范围 | 无异常路径 |
| `handoff` | 下一阶段能直接接着做 | 交了结论但无输入物 |
| 阶段专属 | `decision/convergence/acceptance/ontology/demo/eval/value/release/iteration` | 见 `docs/00` 第六节 |

`passScore = 60`。**模型给分，确认人签结论**；两者不一致时以确认人为准，并记录分歧原因 —— 这条是站点「谁有权批准」的落地。

### 7.5 号源一致性解释（`domain/slot.py` + `domain/slot_rules.py`）

输入：`patient_slot_status`、`hospital_slot_status`、`sync_batch_at`、`campus`、`now`。
输出：`verdict` + `path` + `reason_codes`。

| 判定 | 条件 | 建议路径 |
|---|---|---|
| `CONSISTENT` | 两端一致且属本院区 | 直接刷号 |
| `SYNC_WINDOW` | 夜间同步后 30 分钟内不一致 | 人工核验，窗口内不重挂 |
| `CROSS_CAMPUS` | 号源归属院区 ≠ 就诊院区 | 引导改约/转诊，**不重挂** |
| `CANCELLED_NO_NOTICE` | 院内已取消、无通知记录 | 优先补号 + 工单 |
| `UNKNOWN` | 缺字段或状态机异常 | 拒给结论，转组长 |

**判定与措辞分开的理由**：判定要能逐条回归（harness 断言 `verdict`），措辞要随患者情绪调整。混在一起，改一句话就可能改坏一条判定。

### 7.6 分诊信息补全（`domain/triage.py`）

主诉 → 抽取（年龄、性别、主诉、持续时间、伴随症状、危险信号）→ 规则过滤 → 模型给「科室建议 + 依据」→ 护士确认。

硬约束写死在代码里，不写进提示词：

- 输出必带 `suggestion_only: true`；
- 置信度 < 阈值只输出「建议人工分诊」，不给科室；
- 命中危险信号（胸痛、意识改变、大出血、呼吸困难）→ 直接「立即转急诊」，**不给门诊科室**；
- 结果只能进「待护士确认」队列，不得写 HIS。

### 7.7 留痕记录（`domain/note.py`）

补录、加号、过号处置三类动作 → 结构化记录：`operator_id`、`operator_no`、`action`、`reason`、`related_slot`、`confirmed_by`。
缺工号直接拒（`E-3001`），这是 `EV-130` 的原话要求。

### 7.8 知识库（`domain/kb/`）

- 语料：分诊工作规范（试行）2025 版、门诊排班与号源管理办法（2025 修订）、预约平台操作手册 v3.2（标「与配置冲突，仅参考」）；
- 切片按**条款**切，不按字数切；每片元数据 `doc_id`、`version`、`clause`、`effective_date`、`status`；
- 检索：向量 Top-8 → 条款号加权 → Top-3 入上下文；
- 回答必须带 `[{doc_id} {clause}]`；无依据或条款冲突 → **拒答并转人工**，不许编条款。

### 7.9 harness（`harness/`）

四类套件 + 一条流程回归，全部对齐站点编号：

| 套件 | 用例数 | 对应站点 | 断言什么 |
|---|---|---|---|
| `flow` | 27 + 9 | 27 任务、9 关卡 | 27 条状态迁移、9 条关卡阻断；缺 `evidenceIds` 必须拒收 |
| `interview` | 36 | S2-1 | 六视角 6 问齐全；追问触发正确；未满 36 不许完成 |
| `slot` | 30 | S5-2 业务闭环 | `verdict/path` 精确匹配；跨院区不得出现「重挂」 |
| `triage` | 40 | S5-2 | 科室命中；危险信号必转急诊；`suggestion_only=true` |
| `redline` | 20 | 数据红线 | 出站无姓名/身份证/手机号/病历号原文；违规数 = 0 |
| `kb` | 20 | S5-2 | 引用条款正确；无依据必拒答 |
| `gate` | 9 × 7 | 9 关卡 | 每个维度缺项能被扣分；60 分以下必须 `locked` |

指标：`pass@1`、`pass^5`、拒答率、红线违规数、p95 时延。
门槛：`pass^5 ≥ 0.90`，红线违规 `= 0`，p95 `≤ 6s`（7B + 本地 GPU）。

## 8. 接口设计

### 8.1 统一响应

成功：

```json
{"ok": true, "data": {}, "error": null}
```

失败：

```json
{"ok": false, "data": null, "error": {"code": "E-1002", "msg": "号源字段缺失，无法判定"}}
```

### 8.2 流程域接口（对应 27 任务）

| 方法 | 路径 | 用途 | 对应任务 |
|---|---|---|---|
| GET | `/api/v1/stages` | 九阶段与锁定状态 | 全局 |
| GET | `/api/v1/stages/{stage}/steps` | 该阶段 3 项任务与工具 | 全局 |
| POST | `/api/v1/steps/{step_id}/submit` | 提交作品，校验四字段 | 27 步 |
| POST | `/api/v1/gates/{stage}/review` | 7 维评分 + 确认人签核 | 9 关 |
| GET | `/api/v1/evidence` | 台账检索（按 `EV`/状态/角色） | S2-3 |
| POST | `/api/v1/interview/{role_id}/answer` | 36 问逐问作答并落证据 | S2-1 |
| POST | `/api/v1/interview/{role_id}/probe` | 触发追问（无口径/模糊词） | S2-1 |
| GET | `/api/v1/artifacts/{stage}` | 导出阶段作品 md | S3-1、S4-1 |

### 8.3 业务域接口

| 方法 | 路径 | 用途 | 角色 |
|---|---|---|---|
| POST | `/api/v1/slot/explain` | 号源一致性解释 | 导医、分诊护士 |
| POST | `/api/v1/triage/suggest` | 分诊信息补全 | 分诊护士 |
| POST | `/api/v1/note/structure` | 留痕记录生成 | 导医、分诊护士 |
| POST | `/api/v1/kb/ask` | 制度问答 | 全员 |
| GET | `/api/v1/audit/{trace_id}` | 审计回放 | 门诊部、医务科 |
| GET | `/api/v1/health` | 健康检查（模型 + 知识库） | 运维 |

### 8.4 错误码

| 码 | 含义 | HTTP | 处理 |
|---|---|---|---|
| E-1001 | 参数校验失败 | 400 | 字段级错误 |
| E-1002 | 关键字段缺失，无法判定 | 422 | 转人工，不猜 |
| E-1003 | 阶段作品缺必填字段 | 400 | 指出缺哪个字段，拒收 |
| E-1004 | 引用了不存在的证据编号 | 400 | 拒收，列出无效编号 |
| E-2001 | 无权限访问该数据 | 403 | 记审计 |
| E-2002 | 命中数据红线 | 451 | 拦截 + 告警 |
| E-3001 | 缺少操作人工号 | 400 | 拒绝生成记录 |
| E-4001 | 模型不可用 | 503 | 返回规则结论 + 提示「模型离线」 |
| E-4002 | 知识库无依据 | 200（ok=false） | 拒答 + 转人工 |

> `E-4002` 用 200 是刻意的：**拒答是正常业务结果，不是系统故障**，不能被监控算进错误率。

## 9. 权限矩阵

站点用「买方 / 拥护者 / 操作者 / 阻碍者 / 沉默怀疑者」做利益相关者原型；本仓把原型落到医院岗位，权限按**数据 × 动作**逐格写清：

| 数据/动作 | 导医 | 分诊护士 | 门诊部 | 医务科 | 信息科 | FDE |
|---|---|---|---|---|---|---|
| 号源状态（本院区） | 读 | 读 | 读 | 读 | 读 | 读 |
| 号源状态（跨院区） | 读（仅状态） | 读 | 读 | 读 | 读 | 读 |
| 检查结果 | **无** | 无 | 汇总读 | 读 | 读 | 无 |
| 分诊建议 | 无 | 读写（需确认） | 读 | 读 | 无 | 读 |
| 留痕记录 | 写（带工号） | 写（带工号） | 读 | 读 | 读 | 读 |
| 审计回放 | 无 | 无 | 读 | 读 | 读 | 读 |
| 阶段作品 | 无 | 无 | 读 | 读 | 读 | 读写 + 提交 |
| 关卡签核 | 无 | 无 | G1/G3/G7 | G3/G6/G9 | G5/G8 | 无（只提交，不签核） |
| 一键停机 | 无 | 无 | 可 | 可 | 可 | 无 |

> 两条不许动的边界：
> 1. 导医读不到检查结果 —— `EV-112` 现场事实 + `EV-125` 红线，不是技术限制；
> 2. **FDE 不能给自己提交的作品签核** —— 站点九道关卡全部由业务/技术/风险角色确认，这是「谁承担结果」的落地。

## 10. 数据红线与落地机制

| 红线 | 落地位置 | 验证方式 |
|---|---|---|
| 姓名/身份证/手机号/病历号不进模型 | 入模型前 `redline.py` 替换为 `P-****`，出站再校验一次 | `harness/redline` 20 例，违规即失败 |
| 不进日志 | 日志只落 `trace_id` 与结构化字段，不落原文 | 日志采样 grep 断言 |
| 不出院内网 | 内网部署、模型本地、无外呼 | 出网策略 + 代码层禁外呼 |
| 不可逆动作不自动执行 | 所有写操作产出「草稿」，由人执行 | 接口层无写 HIS 的客户端 |
| 证据不许编 | `evidenceIds` 逐个回查台账 | `E-1004` 拒收 |

**双层脱敏的理由**：只在入口脱敏，中间件一加日志就漏；只在出站脱敏，模型已经「看过」原文。两层都做，任一层失效仍有兜底。

## 11. 本地部署（Ollama）

### 11.1 硬件与前置

| 项 | 最低 | 建议 |
|---|---|---|
| 内存 | 16 GB | 32 GB |
| 显存 | 8 GB（7B int4） | 12 GB+ |
| 磁盘 | 20 GB（模型 + 索引） | 40 GB |
| 系统 | Windows 11 / Ubuntu 22.04 | Ubuntu 22.04 |

### 11.2 启动顺序

```bash
# 1. 拉模型（一次性，之后完全离线）
ollama pull qwen2.5:7b-instruct
ollama pull nomic-embed-text

# 2. 建知识库索引（条款级切片）
python -m app.kb.build --config config.yaml --rebuild

# 3. 启动服务
uvicorn app.main:app --host 127.0.0.1 --port 8000

# 4. 自检：模型、知识库、九阶段状态都要返回 ok
curl -s localhost:8000/api/v1/health | python -m json.tool
```

> 只监听 `127.0.0.1`。对外必须在反向代理层加院内认证，不靠应用层扛。

### 11.3 离线保证

- 模型权重在本地磁盘，`OLLAMA_HOST` 指向本机，不配置远程 endpoint；
- 知识库索引为本地 SQLite，随仓交付；
- 应用层不引入任何需联网的 SDK（无 OpenAI/云向量库）。
